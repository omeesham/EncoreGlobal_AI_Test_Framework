## §3 — Architectural divergence vs new site (cloudapps-e2e.encoreglobal.com)

This is the load-bearing finding of this baseline walk. New site implementation diverges fundamentally from old-site; classification recommendations in §6 flow from these deltas.

| Aspect | OLD site (nav2 baseline, 2026-05-11) | NEW site (per locations_notes_test_cases.md, dated 2026-04-14 + MCP_VERIFICATION_LOG 2026-03-17) | Divergence kind |
|---|---|---|---|
| Surface | Single `<textarea formcontrolname="Notes">` | Multi-row table; each row has its own `<textarea name="notes.notes.{i}.note">` | **Intentional UX change** (paradigm shift: scalar → table) |
| Add control | None (textarea is always present, edit in place) | `<button>Add</button>` scoped via `[data-testid="location-settings-section-notes"]`; click creates new row | **Intentional UX change** (new affordance for multi-note) |
| Delete control | None | Conditional Delete button per row — appears when row has content OR when ≥2 rows exist | **Intentional UX change** (linked to row paradigm) |
| Max length | **1000 chars, HARD** (`maxlength="1000"` HTML attribute — browser blocks input beyond 1000) | **4000 chars, SOFT** (no HTML maxlength; counter shows overage past 4000; paste/programmatic can exceed) | **Intentional UX change** (capacity expansion + enforcement model flip from hard→soft) |
| Char counter | None | Live counter `"X/4000 (N Left)"` updates per keystroke; class `text-[11px]`; no data-testid | **Intentional UX change** (new affordance) |
| Progress bar | None | `<div role="progressbar">` fills proportionally with char usage | **Intentional UX change** (new affordance) |
| Empty state | Empty textarea (default) | "No Notes Available" empty-state row in `<tbody>` until first Add click | **Intentional UX change** (table-paradigm-specific) |
| Selectors | `formcontrolname="Notes"` (Angular Reactive Forms) — zero `data-testid` | `data-testid="location-settings-sub-tab-notes"`, `location-settings-section-notes`, `location-settings-btn-save` (left-panel shared) | **Intentional architectural shift** (selector-discipline introduction) |
| Save button location | Top of page, global (shared across all sub-tabs of Basic Information) | Left panel `[data-testid="location-settings-btn-save"]` (shared across all Location Settings sub-tabs incl. Notes) | Functionally equivalent (both shared/global), positionally different — minor UX |
| Save gating | Direct save on click (no dialog observed on baseline today; could not confirm fully — observation-only per LR-ENC-001) | Save click opens `[role="alertdialog"]` with title "Save Changes" + body "Are you sure you want to save the changes?" + Cancel/Save buttons | **Intentional UX change** (confirmation gate added on new site per LR-012) |

## §4 — Multi-row UX absence (deepest divergence — drives §6 classification)

Old site fundamentally does NOT support the multi-note pattern that the new-site TC file (28 TCs) is largely structured around. ~20 of the 28 TCs reference multi-row mechanics:

- TC-LOC-NTS-026 "Partial deletion persistence — delete middle row, save, verify remaining"

**Classification**: every one of these is **baseline-absent** in the literal multi-row sense — the OLD site has no row paradigm at all. But this is NOT a regression — the old site predates this feature. Per LR-ENC-001: `baselineScope: baseline-absent` is allowed (NOT a HALT) when the feature is net-new on the active site. **The right classification for Phase 2 is `intentional-UX-change`**, not `regression-from-baseline`, because the new-site multi-row paradigm is the documented direction (REQUIREMENTS.md + Jira 1712).

Phase 2 (HEALER) MUST classify the entire multi-row TC cluster as `intentional-UX-change` rather than `baseline-absent` (which would imply escalation to `/encore-questions`). The new-site behavior is the canonical/desired behavior; the old-site single-textarea is the legacy pattern being replaced.

## §5 — Max-length enforcement flip (hard → soft)

The single concrete **regression-from-baseline candidate** worth flagging: old site enforces a 1000-char HARD limit; new site enforces a 4000-char SOFT limit (per TC-LOC-NTS-007 + TC-LOC-NTS-021). This is two flips at once:

1. **Capacity**: 1000 → 4000 chars (4× expansion).
2. **Enforcement model**: HARD (browser-blocking via `maxlength` HTML attribute) → SOFT (counter shows overage; paste/programmatic can exceed 4000).

Per LR-034 bug-filing protocol, this is **NOT a bug** — the new-site behavior is documented and intentional (capacity expansion is positive; enforcement-model flip is a deliberate product choice favoring permissive entry + user-visible counter signal over strict blocking). Phase 2 MUST classify as `intentional-UX-change`.

**However**: if Phase 2 finds the new site rejects pastes beyond 4000 chars in some browsers (i.e. soft limit isn't actually soft), that would be a regression — confirm during Phase 1a.
