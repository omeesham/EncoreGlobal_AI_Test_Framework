## 6. BUG-LOC-PRI-001 baseline reclassification (Corporate Pricing uncheck → revert)

BUG-LOC-PRI-001: on the **new site**, unchecking Corporate Pricing saves HTTP 200 (both calls) but reverts to checked on reload (confirmed app-wide, offices 1604 + 1605, 2026-06-18).

**Baseline behavioral comparison: NOT mutation-tested on the shared baseline — documented decision (not an omission).** Reasons:
1. **Irreversible-corruption risk.** Old-site 1604 has 5 pricebooks ASSIGNED (§3). Unchecking Corporate Pricing cascades to disable+clear the primary dropdowns; the old-site **Save commits the whole location-detail form**. If the assignments clear, restoring them requires re-selecting the exact GUIDs from 483/527-option lists by unknown name — **not reliably reversible** on a shared canonical test office.
2. **Confounded comparison.** The new-site bug was observed with primary pricing **UNSET**; old-site 1604 is **SET** (§3). Corp-Pricing-uncheck persistence may itself depend on pricebook-assignment state, so an old-site uncheck (pricebooks set) would not be measuring the same scenario as the new-site bug (pricebooks unset).

→ `baselineComparison` set to **`not-checked`** (honest per LR-034 + feedback_override_cannot_convert_missing_to_evidence.md — a clean regression call cannot be laundered from a confounded/destructive-only test), with `baselineEvidence` pointing at THIS artifact and recording: the Corporate Pricing **feature is present on baseline** (checked default + cascade, §2), so it is NOT baseline-absent; the persistence behavior specifically was not behaviorally compared for the two reasons above. A clean future comparison would require setting new-site 1604's primary pricing to match old-site state, then testing uncheck-persistence on the **new** site (no baseline mutation) — recommended if regression-vs-intended must be settled.
