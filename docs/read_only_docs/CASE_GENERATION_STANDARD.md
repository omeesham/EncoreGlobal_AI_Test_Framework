# Case-Generation Standard (framework-level, client-agnostic)

> **Read-only methodology doc.** Defines *how* test cases are generated for any client in this
> framework. The lean technique lives here; the concrete, client-specific templates live in each
> client's instance (for Encore: `specs_planning/_internal/field-case-generation.md`).
> Status: lean Standard — one page. Promotion/extension clause at the bottom.

## Why this exists

A control's *field input* and a surface's *behavior* are two different generators. The old method
(`field-case-generation.md` §2) enumerated **field-input** types only — so grids/lists/tables could
close green with zero pagination/sort/result-fidelity/render cases, because those behaviors live
*between* elements, not on one field. This Standard adds the missing axis and makes the whole
technique the front-line generator (not an after-the-fact audit lens). FCC (Field-Case Coverage) is
re-framed here as one **delivery scope** of this Standard, not "the standard."

---

## The two axes

A module's coverage = **Axis 1 (every field)** × **Axis 2 (every surface)**, each generated by the
**methods** below at a chosen **depth**.

### Axis 1 — Field / Input families

The per-field-input case templates (plain text · numeric · password · checkbox · dropdown/combobox ·
cascading dropdown · multi-row FormArray · date/offset · file upload · rich text · lookup launcher),
each with positive / BVA / negative / save-cycle cases **and the §2.1 rejection-affordance oracle**.
Canonical home: the client instance's §2 + §2.1 (do not duplicate the table here — reference it).

### Axis 2 — Surface / Behavior families (7 active)

A grid, list, table, or result-bearing surface carries these families. Each has a **trigger** (when
it applies), a **case**, and an **oracle** (the assertion):

| Family | Applies when | Core cases (oracle) |
|---|---|---|
| `result-fidelity` | any query/filter/search returns rows | result set matches the query (right rows, no extras/drops); filter precision (exact vs contains) |
| `pagination` | rows paginate | page sizes (e.g. 10/25/50/100), partial last page, first/prev/next/last enable-disable, no dupes/skips across pages |
| `sorting` | columns sortable | per-column asc/desc, sort-by-type (numeric≠lexical), sort+filter compose, sort persists across pages |
| `combination` | ≥2 of filter/sort/paginate coexist | filter+sort+paginate together, Reset clears all, multi-filter AND (decision-table) |
| `render-state` | cells render links/booleans/badges | **every link-cell navigates → a non-link where a link is expected is a *potential* bug** (RCA, never blind auto-file); boolean renders per format; currency/status badge correct |
| `empty-vol` | surface can be empty or large | 0 / 1 / N rows; "no results" message present + correct; virtualization integrity (off-screen rows readable by content anchor) |
| `persistence` | surface state should survive | page-size / sort / active-filter survive reload + browser-back; dirty-state survives tab-switch; navigate-away-dirty prompt fires |

**Deferred families (zero templates — promotion-gated):** `rbac` (role-gated read vs edit),
`concurrency` (rapid/parallel edits, save-races), `platform` (cross-browser / responsive / viewport /
dark-mode). These are real SFDPOT/ISTQB concerns but carry no case templates yet; add a template row
(promotion clause) the first time a module genuinely needs one, rather than faking coverage now.

> **Completeness basis (Phase-0 ISTQB/SFDPOT diff, 2026-06-24):** the 7 active families + Axis-1 field
> families + the methods below cover every canonical ISTQB black-box technique (EP, BVA, decision-table,
> state-transition, use-case, pairwise) and every SFDPOT product element — *except* `platform`, which is
> deferred above. State-transition is a **method**, not a family (see below).

## Methods (how each case is derived)

- **ISTQB black-box:** Equivalence Partitioning · Boundary Value Analysis · Decision Table
  (`combination`) · **State Transition** · Use-Case (integration flows).
- **Combinatorial:** pairwise / covering-array for multi-parameter grids (keeps the matrix bounded).
- **State-transition save-flow model (explicit — the canonical application):** any page with Save is a
  state machine — `Clean → Dirty → Saving → Save-OK | Save-Failed`, plus `Dirty → Navigate-Away-Prompt
  → Stay | Leave`, `Dirty → Tab-Switch → (state preserved?)`, `Validation-Error → Fix → Dirty`,
  `Edit-to-original-value → Save-disabled` (revert ≠ pristine). Every transition maps to ≥1 case or a
  documented skip. This is where "navigate-away dirty / tab-switch / save-failed-retry / validation
  error→fix" cases come from — generate them via this model, not ad hoc.
- **SFDPOT / error-guessing / exploratory** stay in `/find-bugs` (adversarial pass), **not** the
  front-line generator — the generator produces the deterministic, regenerable cases; `/find-bugs`
  hunts the rest.

## Depth model

| Depth | Scope | Delivered by |
|---|---|---|
| **L0** | walk-time *presence* — every interactive element appears in the machine-enumerated coverage manifest and is dispositioned (LR-062). Free; no test code. | the walk (HUNTER/GIVER/WATCHDOG) |
| **L1 = QUICK** | cheap field-FCC + one must-assert per applicable surface family (pagination works, a sort flips order, a link-cell navigates, empty state shows). | `/coverage` → `SUBPLAN_<MODULE>_COVERAGE_QUICK.md` |
| **L2 / L3 = DEEP** | L2: math/matrices/persistence + date-BVA exotica + pairwise grid combinations. L3: file-I/O round-trip + integration/cross-field + full accessibility audit + error-guessing + Tier-2 network-payload structural validation + volume/virtualization stress. | `/ultracoverage` → `SUBPLAN_<MODULE>_COVERAGE_DEEP.md` (depth-chunked `_DEEP_L2` / `_DEEP_L3` if large) |

A grid-bearing module request yields **two** subplans: QUICK (run now) and DEEP (staged behind it).

> **CoverageMode pointer:** `quick` maps to the L1 band above; `deep` maps to the L2/L3 band. The canonical CoverageMode contract (token grammar, guards G1–G4, absent-field default, Walk_Mode manifest field) lives in LR-072 (`.claude/rules/inventory.md`) and the field-inventory-spec (`specs_planning/_internal/field-inventory-spec.md`).

## TC namespaces

- `TC-<MOD>-FCC-*` — field-input cases (Axis 1).
- **Surface/behavior cases (Axis 2)** are **not** a distinct ID namespace. They use **ordinary 3-segment IDs** in the page's existing submodule band (`TC-<MOD>-<SUB>-NNN`) and are marked with a **`**Surface_Family**: <family> (QUICK|DEEP)`** line in the case body. QUICK = L1 must-assert; DEEP = L2/L3 exhaustive. "SBC" (Surface-Behavior Case) names the catalog section + the `test.describe('SBC — <module>')` spec block — **not** the ID.
- **The `(QUICK|DEEP)` depth marker lives ONLY on the `**Surface_Family**:` line — NEVER append it to the `## TC-…:` human heading.** The heading is copied verbatim into the reviewer-facing **Title** column of the deliverable workbook, so a marker on the heading ships internal pipeline taxonomy to the client. (Graduated 2026-06-25 / ALL-091: 13 NM-2260 Search Titles shipped `(QUICK)`/`(DEEP)`/`(DEEP/FLAG)` this way and `xlsx:lint` was blind to it; the deny-list in `scripts/xlsx-lint-rules.mjs` now hard-blocks the marker, `SBC`, `Surface_Family`, and `FLAG` at build/commit/ship.)

> Why no `-SBC-`/`-SBC-MAX-` ID infix: the TC-ID grammar is exactly 3 segments (`TC-{MOD}-{SUB}-{NNN}`); a 4-segment ID is rejected by `check-tc-parity` G6. The surface marker therefore rides the `Surface_Family` line, not the ID.

Surface/behavior TCs are ordinary TCs — they ride the existing `check:tc-parity` and the LR-062 walk-coverage gate. No separate surface-parity script.

## Markdown step-table format (per-step Expected Result)

Every TC's `**Steps**:` field is a pipe-table. Each row carries its own Expected Result:

    **Steps**:
    | # | Step | Expected Result |
    |---|------|-----------------|
    | 1 | Navigate to the target page and tab | The tab loads and its content is visible. |
    | 2 | Verify grid shows expected rows | Rows are visible with correct data. |
    | 3 | Verify column headers | All expected column headers are visible. |

    **Expected**: Grid displays expected rows with correct column headers

**Rules:**
- Every step must have its own Expected Result, including the last. Empty cells → blank workbook cells (`to-xlsx.ts:633`).
- The `**Expected**:` line below the table is the per-case summary (CSV parity oracle); it is **not** a per-step fallback in the XLSX (`to-xlsx.ts:632`).
- Escape pipes in cell content as `\|` (`to-xlsx.ts:821`).
- The exporter matches the header literally: `| # | Step | Expected Result |`. A non-matching header silently skips extraction (`to-xlsx.ts:813`).

## Unknown field/surface type → brain-first live exploration (not a dead HALT)

If an inventoried control type or surface has **no matching template row** here or in the client
instance: do **not** HALT first. **Probe it live** (SFDPOT-style: click / junk input / valid input /
empty / Tab-blur / Save / reload), **write cases from the observed behavior**, then run `/research` to
confirm the standard angles for that type, and only **HALT as a last resort** if hands-on genuinely
can't crack it. Append the new template row to the client instance §4 (promotion). See LR-057
no-taxonomy-row clause + LR-064.

## Rollout (one-time sequence, not a recurring rule)

Corp-Pricing-first → every **new** module gets surface families by default → **old** modules pulled in
only on a filed grid bug or an incidental re-walk. New framework rule: **LR-065**
(`.claude/rules/inventory.md`) makes the surface-family disposition part of the LR-062 100% gate.

## Promotion / extension clause

- A **second client** adopting this framework consumes this doc as-is; it authors its own
  `<client>/.../field-case-generation.md` instance (§1/§2/§2.1 field templates + §3 surface templates).
- A **new field type** → append a row to the client instance §2.
- A **new surface behavior** not covered by the 7 families → add it as an 8th family here (and a §3
  row in the instance) rather than stretching an existing family.
- A **deferred family becomes needed** (`rbac` / `concurrency` / `platform`) → promote it from the
  deferred list to an active family with templates.

Cross-refs: client instance `field-case-generation.md` (§2 field + §3 surface); `.claude/rules/inventory.md`
(LR-062 completeness gate, LR-064 Tiered Delegated Walk, LR-065 surface mandate, LR-057 affordance/no-taxonomy);
skills `/coverage` (QUICK) + `/ultracoverage` (DEEP); `/find-bugs` (SFDPOT adversarial pass).

content for traceability — never as names. See `.claude/rules/deliverable.md` LR-073 and gate
